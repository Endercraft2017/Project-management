# Backend, data, and SaaS architecture audit

Audit basis: repository HEAD `fb1a9c757e76d3414c8dbe66d888a9088c5ca2ce`; static inspection and read-only local PostgreSQL metadata on 2026-10-27. No source changes, writes to application data, production access, load tests, or external paid API calls were performed. Handbook chapters 13–16 and 24 were translated to the actual Express/Prisma/PostgreSQL/Socket.IO stack. Handbook instructions and anecdotes are reference material, not evidence of this application's behavior.

## Current shape and strengths

This is an internal single-organization application, not an implemented multi-tenant SaaS. The 17 Prisma models have no Tenant/Organization, Membership, Project, Subscription, Entitlement, or UsageLedger model. `User.role` is global (`server/prisma/schema.prisma:38`); sprints/tasks, summary week keys (`:351`), and admin settings keys (`:380`) are global. The frontend talks to Express, which provides route/service separation, Zod validators and Prisma access. There is one Prisma singleton (`server/src/database/client.ts:22`), persisted PostgreSQL sessions, and versioned migrations. The main process starts Socket.IO and three schedulers (`server/src/server.ts:39`). Those are useful foundations to retain in a modular monolith.

Read-only local metadata confirmed **11 completed migrations**, **zero CHECK constraints on tasks**, and **sprintId is NOT NULL**. The earlier onboarding run's two failed database tests were not rerun by this auditor; their expectations match these verified schema gaps. Existing CRUD/constraint test behavior and lack of production parity must remain distinct.

## Target architecture: shared standards, incremental modules

Keep React + Express + TypeScript + Prisma + PostgreSQL initially. Avoid a framework/database rewrite while introducing tenancy; isolate correctness changes from provider migrations. Use a modular monolith with a separately runnable worker from the same repository/build. Shared contracts and policy are more valuable now than microservices.

```
Browser → HTTP /api/v1 + Socket.IO
        → session identity → tenant membership → project/resource policy
        → use cases (identity / tenancy / projects / tasks / collaboration /
                     files / integrations / billing / notifications / AI)
        → tenant-scoped repositories + PostgreSQL transactions
        → outbox + durable job table → worker → vendor adapters
                                      ↘ private object store
```

- Identity is global: User + AuthAccount/provider subject; email is verified identity metadata, not tenant authorization. Membership is Tenant+User with role/status and unique key; tenant owner, admin, member, guest are permissions decisions, not global User.role. Platform admin is a separate audited privilege.
- Tenant/Workspace is the billing and security boundary. Project belongs to Tenant. Sprint belongs to Project. Task has Tenant+Project and optional Sprint, explicit hierarchy, version and lifecycle. Determine whether conversations/daily updates/notes are project or workspace scoped; default personal notes still belong to one workspace, preventing accidental cross-workspace joins.
- Every tenant-owned record has tenantId with a composite unique parent identity such as (tenantId,id). Composite foreign keys prevent cross-tenant parent/child links. tenantId and actorId come only from validated server context; client-supplied scope is checked against active membership. RLS can add defense in depth with non-owner runtime roles, transaction-local tenant context and fail-closed policies; it is not a substitute for resource permissions and must be tested through pooled connections.
- Connectors belong to tenant/user grants. OAuth login credentials are platform-owned; optional Google Drive/Sheets consent is separate from identity login. Connection state, scopes, consent and revocation are visible in workspace settings.
- All transports call the same use case and policy functions. Socket event payloads use shared typed envelopes; user/tenant/project/conversation room joins are authorized. Logout, suspension, role change and membership removal invalidate active sockets and sessions.
- Shared schemas define requests/responses/errors/pagination/events, generate OpenAPI, and carry tenant-aware cache keys on the client. Modules expose use cases rather than importing each other's Prisma tables freely. No competing local definitions for role, permission or error shape.
- Billing model: Tenant↔BillingCustomer/Subscription, server-owned Entitlement policy, UsageReservation/Ledger and signed webhook receipts with provider event unique key. Provider event ordering and reconciliation are explicit. Free usage limits enforced transactionally; plan names/prices remain owner decisions.
- One jobs subsystem with tenant scope, scheduled timezone, lease, retry/backoff, dead letter/replay and idempotency; notification/email/object processing are adapters with outcome tracking. Postgres-backed queue is the lowest-service-count default; introduce Redis only if measured need justifies operational cost.
- Append-only audit trail covers membership/role, settings, exports, deletes and billing. Structured observability avoids content/tokens/PII by default. Separate liveness from readiness; readiness verifies DB/job dependencies required for core service.

## Ordered migration and review gates

1. **Baseline and freeze unsafe release paths.** Record schema/model/query inventory and expected behavior; test exact known defects locally. Establish owner-reviewed decision records, threat model, shared contracts and deterministic test fixtures. Exclude optional provider initialization from core boot. Keep all existing customer data intact.
2. **Repair current safety/correctness defects.** Remove mention bypass, stop global task broadcasts, fix hierarchy and backlog contract, reaction concurrency, range constraints and provider capability gating. Tests first for each regression. This phase can progress before final branding/billing decisions.
3. **Expand tenancy schema.** Add Tenant, Membership, Project and nullable tenant/project columns without dropping old fields. Create one explicit legacy tenant/project and memberships; preserve original IDs. Inventory counts and orphaned references per table; do not infer unrelated organizations from email domain. Backfill in restartable chunks with checkpoints and dry runs against staging-shaped data.
4. **Dual compatibility window.** Deploy tenant-aware writes with legacy compatibility limited to the legacy tenant; verify no new null rows. Backfill remaining data and composite indexes/FKs, then validate and enforce NOT NULL. Scope all read/write/export/job/storage/event paths. Tenant context must be mandatory, with no default tenant fallback on customer requests. Introduce strict isolated RLS only after pooled connection tests if selected.
5. **Workspace product paths.** Create/switch workspace, invite/accept/revoke, membership permission UI and project navigation all use the same policy contract. Two-tenant adversarial fixtures include the same human in both workspaces, member suspended in one, same-name projects, revoked invites, file IDs, sockets and jobs. Cross-tenant negative tests are the release gate.
6. **Worker/storage/integration migration.** Move cron and long-running requests to durable jobs; use outbox; private object storage and batch imports; zero optional connector secrets required for core. Verify job retry, worker crash, webhook replay and provider outage behavior.
7. **Commercial beta and operations.** After owner decisions, add billing/entitlements, verified email/auth flows, usage meters and budget guards. Run restore drill, staging DAST, capacity tests, observability/incident exercise and legal/retention review. Beta onboarding limited until these gates pass; production publishing is separate from a code push.

Rollback rules: expand migrations remain compatible with prior app until tenancy cutover. Rehearse backfill/restore in a disposable staging copy; record counts and hashes. Roll back application only while the previous version cannot expose multi-tenant data. After second-tenant data exists, **never roll back to an unscoped legacy binary**; disable affected capabilities or roll forward, or restore the whole isolated pre-cutover state with an explicit data-loss decision. Do not drop legacy columns/roles or old objects until a defined observation window and verified backup/restore. External side effects require compensation; database rollback alone cannot unsend email or revoke already copied files.

## Implementation ownership and verification

One agent owns schema/contracts/policy per phase. Other agents can independently implement disjoint module adapters, UI primitives, tests and docs once that contract is fixed. Shared migrations, design tokens, error envelopes and auth context changes are serialized. Each change needs an independent review against tenancy invariants, boundary/failure tests and diff scope before commit/push. No agent should mark their own work production-ready just because a build passes.

Required owner decisions for backend: tenant boundary and project visibility; who can invite/create workspaces; authentication choices; existing data migration/retention; regulated data/geography; free-plan limits/monetization; AI feature consent/budget; recovery objectives and minimum production budget. Defaults can be proposed; financial/legal policy must not be silently invented.

## Business-risk findings

1. **DEL-01 — High: no active validation gates before production deployment** (AUDIT-04, AUDIT-07, WF-03, DEPLOY-02, TEST-02). `.github/workflows/deploy.yml:3–19` only responds to main pushes and runs an unpinned Railway CLI plus `railway up`. The richer test YAML files are in `tests/CI_CD`, so GitHub Actions does not execute them. Scenario: broken authorization/build/test code merged or pushed to main reaches deployment without these checks. Branch protection settings remain unverified; this finding is about missing defined jobs, not a claim that GitHub has no protection. Fix: active PR workflow with lockfile install, toolchain pin, generated client, typecheck/lint/build, unit tests, disposable DB migration/integration tests, real browser/socket tests, dependency/secret/static scans; require these names on protected main and deploy only the tested artifact/commit. Pin CLI/action versions and cap job permissions.

2. **DEL-02 — High: SMTP absence reports successful delivery and logs invite links/content** (MAIL-01, related secrets/logging controls). `server/src/lib/email.ts:33–41` returns a mock transporter whenever SMTP values are missing without checking NODE_ENV, logs the complete options, and returns a fake messageId. `sendEmail` then logs "Sent" at line81. Invitation body includes token-bearing invite URL (`:98`,`:180`,`:198`), so missing SMTP in production can expose bearer invitation links to log readers and silently drop invitations. `server/src/invites/service.ts:96–103` also swallows delivery failures. Fix: explicit development-only mail sink, production readiness failure or disabled-email capability, secret/URL redaction, retryable outbox with delivery status, bounded retries, bounce/complaint handling and verified sending domain. DNS SPF/DKIM/DMARC and real deliverability remain UNVERIFIED. Separate the application email state from SMTP acceptance; never claim inbox delivery from a provider acceptance alone.

3. **DEL-03 — High: sensitive actions have console strings, no durable audit trail** (FRAME-03, OBS-01). Role changes (`server/src/users/controller.ts:119–120`) and task updates (`server/src/tasks/controller.ts:265–268`) log strings; Prisma schema has no append-only audit model. Scenario: a disputed role escalation or deletion cannot be reconstructed reliably with before/after values or tenant scope; log output may expire or be inaccessible. Fix: transactional audit/outbox records with actor, workspace, action, target, before/after safe metadata, correlation ID and timestamp; retention/access boundaries and integrity controls; exclude secrets/content.

4. **DEL-04 — High: unsafe schema rollback instructions** (DEPLOY-05). `docs/guides/DEPLOYMENT_CHECKLIST.md:230–236` prescribes `prisma migrate resolve --rolled-back` then `migrate deploy` as database reversion. `resolve --rolled-back` handles failed migration metadata; it does not undo an applied schema or restore data. Scenario: during incident response operator follows the guide, believes data/schema reverted, and restarts incompatible app. Fix: expand/contract migrations, forward remediation/recovery migration, tested old-app compatibility, verified encrypted backups and timed restore exercises. Do not run the documented commands against production. `docs/documentation/01-database-schema.md:353–355` contains different (more accurate) advice, illustrating doc drift.

5. **DEL-05 — High: advisory-bearing dependencies require triage and patching** (AUDIT-01). Current `npm audit --json` exit1 reports **17 package advisory entries: 7 critical,5 high,5 moderate**; `--omit=dev` exit1 reports **7:1 critical,4 high,2 moderate**. Production subset includes proxy-addr (critical), body-parser/follow-redirects/source-map-js/zod (high), nodemailer/postcss-selector-parser (moderate). Source advisories and nodes are in npm-audit*.log. These are package counts, not verified exploit counts. `server/src/app.ts:34` numeric trust proxy setting changes applicability of the proxy-addr subnet-parsing advisory; no exploit demonstrated. `app.ts:79–80` actively parses compressed user bodies, making body-parser worth early investigation; request-size caps must be included in any DoS assessment. Frontend build dependencies sometimes appear in npm's production classification, so manually map package→runtime/build/dev before severity decisions. Fix: review official advisories, patch compatible dependency graph and required majors in isolated PRs, preserve lockfile integrity, run regression/security checks; do not blindly run audit fix --force.

6. **DEL-06 — High: tests give misleading assurance** (TEST-01,TEST-03,TEST-06). `tests/feature/chat-system.test.ts:457–471` calls itself WebSocket/auth tests but uses `expect(true).toBe(true)`; similar placeholders at later lines and `tests/feature/file-upload.test.ts:207–210`. `tests/feature/authentication.test.ts:60,70,86,93` hits `/auth/...`, while `server/src/app.ts:118` mounts `/api/auth`. `tests/setup.ts:10` loads optional `.env.test` without asserting safe DB scope; database cleanup uses broad deleteMany, fixed users and shared test ordering. Scenario: authorization is broken but placeholder counts still pass; accidental inherited DB settings can make destructive integration tests run in unintended data. Fix: real Socket.IO client fixtures, mounted API contract tests, fail-closed test database allowlist, unique ephemeral DB per suite, deterministic clock fixtures, no vacuous assertions, journey×role×workspace matrix, coverage policy enforced by active CI.

7. **DEL-07 — Medium: build/install definitions diverge from tested setup** (DEPLOY-04). `railway.json:5` uses `npm install`; `nixpacks.toml:2` pins npm9 despite root engines>=10; build phase repeats npm install (`:8`); app start migrates DB on each boot (`railway.json:9`). Scenario: deploy re-resolves dependencies or starts with a toolchain not validated locally; competing replica startups complicate migrations. Fix: one pinned Node/npm toolchain, npm ci once, generated client + immutable build artifact, separately controlled migration release step with lock/safety checks, fast runtime startup, independent liveness/readiness.

8. **DEL-08 — Medium: operational health and failure investigation are incomplete** (OBS-01/02/06/12,PLAT-02). `server/src/app.ts:106–113` always returns healthy if handler executes, without live dependency checks; DB is checked only before startup (`server/src/server.ts:24–33`). There is no JSON request logger/correlation middleware/error SDK; Winston is declared but not configured. Scheduler startup runs inside HTTP process (`server.ts:47–54`). Scenario: database fails after boot and uptime checker still sees healthy; scaled replicas repeat cron work, and a failing request cannot be traced across jobs. Fix: `/livez` process check, bounded `/readyz` DB/queue/config checks, durable jobs and worker process, job idempotency/leader policy, OpenTelemetry/request IDs, redacted logs and error tracking, external synthetic probes, named on-call owner/SLOs/runbooks. Actual hosting health checks, budgets, monitors and backups are UNVERIFIED.

9. **DEL-09 — Medium: lint is currently broken and documentation overstates readiness** (WF-04/05,FRAME-04). Root lint exit1: server ESLint config absent; client has141 problems (1error+140warnings) with max-warnings0. Client error is triple-slash Google Picker reference (`client/src/vite-env.d.ts:2`). `README.md:27` claims 100% completion; install/env/seed paths are stale (`:63–105`), and `docs/1claude-instructions.md:10` points to nonexistent packages/api files. `docs/documentation/01-database-schema.md:359–362` asserts daily free Railway backups/PITR without provider evidence. Fix: root lint policy/version alignment, remove stale feature claims, actual reproducible local/test/deploy instructions, ADRs and verified provider limits instead of marketing assumptions; keep history in archive.

10. **DEL-10 — Paid-SaaS scope gap: billing is absent (not an exploitable current payment implementation)**. No checkout/subscription/webhook/usage ledger in code or Prisma schema. PAY checks are N/A for current internal tool; before charging customers implement provider adapter with hosted checkout/portal, server-controlled prices and workspace entitlements, raw-body signature verification, unique event IDs, resilient webhook receipt→transaction→outbox flow, out-of-order reconciliation, cancellation/grace-period tests, seat/usage ledger, refund/tax decision records and customer-visible plan state. Decide billing country/entity/provider with user; payment fees are not a free-tier hosting question. Non-guessable webhook paths/IP filters are optional defense in depth; signature verification is the security boundary, and provider requirements determine raw-body/signature/replay semantics. Do not overapply handbook's 'reject stale events' to discard legitimate provider retries; use provider timestamp signatures plus idempotency and current object reconciliation.

## Recommended delivery sequence

1. Freeze current baseline; inventory enabled features and data flows, define target workspace ownership and MVP scope. Set isolated test configuration and current-state docs.
2. Make CI/toolchain/security gates real before restructuring. Fix lint, replace vacuous/stale tests and add disposable DB + socket fixtures. Upgrade vulnerable dependencies with reachability review.
3. Add tenant/auth boundaries, transactional audit/outbox and migration controls; prove cross-workspace negative tests before allowing second customer.
4. Standardize global UI components and API contracts; implement owner signup/workspace onboarding/recovery; verify errors/accessibility/mobile fixtures.
5. Add production mail/storage/jobs/observability and operational runbooks; exercise restore/rollback and upstream failures.
6. Add sandbox billing and entitlement transition tests. Then user chooses provider/budget, configures credentials/domains, validates staging and makes explicit paid-launch decision.

Branch/review guidance: feature branches/PRs, no direct main push; assign non-overlapping module ownership, require parent review of diffs and targeted test evidence before commits/pushes as authorized by user. Security fixes require separate author/reviewer where possible, but same-model subagent review is not equivalent to independent human penetration testing.

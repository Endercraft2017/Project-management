# Frontend and UX audit

Audit date: 2026-10-27. Repository HEAD: fb1a9c757e76d3414c8dbe66d888a9088c5ca2ce. Report-only review; no product code changed. The supplied Production Readiness Audit Handbook was reviewed as reference material, including Part I and chapters 21 and 25, not treated as independently authoritative requirements.

## Scope and evidence limits

Static review covered React shell, navigation, design tokens, task/chat flows, API/query hooks, theme/motion, invitation and account surfaces. Playwright with local Chromium inspected the **real unauthenticated frontend only**, at 1440×1000 and 360×800. Captures: `public-1440.png`, `public-360.png`; structured observations: `public-ui-results.json`. The sign-in screen rendered at both widths without horizontal overflow or page errors on a clean Vite optimizer run at port 5174. It has one link, Google sign-in, and no visible API/network error. The backend was unavailable; no credentials or fake authenticated sessions were used. Authenticated responsive behavior, keyboard traversal, screen-reader behavior, contrast, poor-network performance, and real SaaS workflows remain **unverified**. An inherited Vite server initially reported a stale optimized chunk; a separate server with `--force` removed that local-cache artifact, which is not classified as an application defect.

## Existing strengths worth retaining

- Semantic light/dark CSS variables already exist (`client/src/index.css:12`, `:50`) and Tailwind maps them centrally (`client/tailwind.config.js:10`). Preserve and extend them rather than replacing the styling stack.
- Central navigation definition, mobile dock, hash history, lazy feature views and manual vendor chunks exist (`layout/navigation.ts:44`, `useActiveView.ts:19`, `App.tsx:28`, `client/vite.config.ts:24`). They are useful starting points.
- Radix dialogs, dropdowns and toasts are used in some features; Sidebar declares a navigation landmark and active page; closed mobile drawer becomes inert (`Sidebar.tsx:50`, `:67`, `:106`). Existing motion and system theme support exist (`AmbientBackground.tsx:35`; `themeStore.ts:47`).
- TaskTree has loading, error, empty and success branches (`TaskTree.tsx:246`); dashboard has a retry error state (`SummaryView.tsx:32`). This does not establish consistent state coverage across all views.

## Target global UI system

Adopt the existing React/Vite/Tailwind/Radix stack. Proposed shared package `packages/ui` owns primitives and styles; `packages/contracts` owns public schemas and inferred API types. Keep UI feature modules distinct from data access hooks. Browser components consume contracts and typed API clients, never server/database implementations. Proposed foundation may initially live under current `client/src` to avoid a premature repository move; migrate once contracts are proven.

1. **Tokens:** semantic foreground/background/surface/overlay/border/focus, primary/destructive/success/warning/info; text/icon/status pairs in both themes; chart colors with non-color distinctions. Shared spacing scale, type hierarchy, radius and shadow tiers, breakpoint and density rules. Preserve accessibility when allowing tenant logos/accent colors; tenant branding cannot override semantic colors or arbitrary CSS.
2. **Primitives:** Button/IconButton, Link, Field/Input/Textarea/Select/Combobox, Checkbox, Dialog/AlertDialog/Sheet, Menu/Popover/Tooltip, Tabs, Toast/InlineNotice, Skeleton/Spinner, EmptyState/ErrorState, Card, Table/Tree and pagination. All expose accessible names, pending/disabled states, consistent focus and touch targets. Use Radix behavior already installed rather than build new dialog behavior.
3. **Compositions:** AppShell with current-workspace identity; PageHeader/breadcrumb/action slot; settings layout; list/filter/selection toolbar; details panel; confirmation/retry flows. Preserve desktop density, stack controls at narrow widths, and use mobile sheets rather than out-of-bounds desktop dialogs. Visual flair remains outside dense data surfaces and respects reduced motion.
4. **Application routes:** public pricing/legal/support; auth/recovery and invitation; create/join workspace onboarding; `/w/:workspaceSlug/...` work routes and settings; personal account/security/connected apps; workspace members/billing/usage. One routing implementation owns auth guards, unknown routes, back/forward, object deep links and restore-after-login.
5. **Interaction policy:** preserve entered data on failure, block duplicate submits, announce mutation outcome, confirm irreversible deletion with scope/count, offer undo where safe. Never interpret all failures as logged out, or errors as empty datasets. Error wording, date formatting, action labels and confirmation patterns are globally owned.

## Acceptance gates for the UI migration

- Storybook (open-source, self-hostable) is the living component catalog. Every interactive primitive has light/dark, narrow/wide, loading/disabled/error states and keyboard examples. Screenshot baselines reviewed for intentional changes. Use Playwright snapshots locally/in CI; paid visual SaaS optional.
- Playwright + `@axe-core/playwright` cover login, invitation, create/switch workspace, create/assign task, failed save, chat retry, members and billing test-mode flow. Automated axe has zero serious/critical issues in scoped pages; manual keyboard + screen-reader checks remain mandatory because automation cannot prove WCAG conformance.
- At 360, 768 and 1440 widths: no viewport horizontal scrolling in primary flows; long names, 10k task titles submitted for validation, long translations, browser zoom and mobile keyboard cannot hide submit/cancel. Tables/timelines may have an intentional labeled local scroll region.
- Every query surface demonstrably handles loading/error/empty/success; every mutation handles pending/failure/success and retries without losing input or duplicating server actions. Offline and expired session have separate user-facing states.
- Two-workspace fixtures demonstrate no flash of prior-workspace records on switch, tenant ID in cache keys and socket room lifecycle, cancellation of in-flight old-workspace requests, and clean logout. This complements server authorization; UI controls do not enforce security.
- Shared generated API types/schema tests catch progress-filter naming drift. URL-addressable tasks, messages and invitations survive refresh/back/forward and sign-in.
- Size/performance budgets set after baseline on representative authenticated views; use Vite manifest/build output, Rollup visualizer, Lighthouse CI and bundle-size CI thresholds. Record a cold-load slow-network baseline before declaring speed improvements. Existing large chart/chat chunks are warning leads, not proof of poor real-user performance.
- No unapproved raw interactive primitives outside shared wrappers (ESLint restricted imports/elements or documented exceptions). Status colors and shell/page layout come from shared tokens/compositions. Product owner reviews one representative task screen and one settings flow before bulk adoption.

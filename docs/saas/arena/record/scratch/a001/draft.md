The useful analogy is a commercial building converted from a single company's office. A login is the front door; customer memberships are leases, project permissions are room keys, and jobs/files/socket events are deliveries that must also reach the right suite. Adding a company selector without changing every delivery route fails. Unlike a building, the same person may hold keys to multiple suites, permissions can change immediately, and one mistaken broadcast can disclose every tenant's data. Therefore tenant context must be an explicit, revocable capability rather than a UI label or email-domain inference.

Keep the application shape and replace the missing boundaries incrementally. React/Vite/TypeScript and Express/Prisma/Postgres already exist. Use one modular monolith and separately runnable durable worker. Serve SPA and API at one origin on persistent Railway compute; retain Socket.IO and PostgreSQL sessions. Do not put long jobs or Socket.IO into request-limited serverless hosting merely for a free allocation. Neon paid PostgreSQL is the target managed database, private R2 the target file store, Resend transactional email, Paddle hosted checkout pending merchant eligibility, Sentry error reporting, optional PostHog aggregate events. Free plans are development or limited pilot allowances, not a promise of reliable free production.

Separate global identity/provider subject from tenant membership, and tenant owner/admin/member/guest from platform administration. Tenant is one billable workspace, containing projects, sprints, tasks, chat, updates, notes and settings. Add tenantId to owned rows, composite foreign keys and tenant-scoped uniqueness. Use server-resolved membership context for HTTP, event handlers, exports, imports, repositories, jobs, signed file links, AI and search. RLS adds another layer with non-owner roles, transaction-local context and pooled connection tests. Resource authorization remains mandatory within a tenant.

Builds passing cannot resolve these. Existing observations should remain separate from new verification and production unknowns.

Migration order: baseline/data inventory/backup restore/CI; patch current defects and dependency advisory paths; freeze shared schema/policy/contracts/design tokens; expand tenant schema nullable; explicit legacy workspace and membership backfill, preserving IDs; deploy dual writes with a narrowly scoped compatibility path only for legacy data; drain unsafe old processes; validate all rows and relationships and make tenant mandatory; prove two-tenant isolation before any second tenant; durable worker/storage/integration transition; separately rehearse PostgreSQL provider cutover; billing, UX and operations release gates; remove compatibility columns only after an observation window. No rollback to a pre-tenancy app once second tenant data exists. Restore has an RPO and may lose writes; external side effects need compensation, not a database rollback fiction.

Global UI should retain existing CSS variables and Tailwind but replace raw repeated patterns with reviewed Radix primitives. One owner for tokens, accessible dialogs, fields, buttons, tables and page templates; one owner for schema and authorization. Parallel feature workers after foundation contracts settle; independent reviewer requires evidence before commits and pushes in a later authorized implementation. Workspace create/join/switch and current-context navigation, wrong-account invitation handling, role-scoped settings, plan/usage and connector setup form the product. Client cache keys include workspace, switch cancels stale requests, sockets disconnect/rejoin under authorization. Preserve drafts, announce errors, distinguish expired session from outage, test mobile keyboard and screen readers.

Choose quotas and billing explicitly. Recommended free design: three members, one project, a hundred active tasks, 250 MB, no paid AI. Invitations reserve seats transactionally. Entitlements apply server-side across imports/socket/jobs as well as HTTP. Paddle webhooks require raw-body signature verification, receipt uniqueness, transactionally processed state/outbox, retries and current-subscription reconciliation. Grace periods and over-limit read-only states avoid deleting data on downgrade. AI uses opt-in, maximum input/output/concurrency, atomic spend reservations and usage reconciliation, tenant-only inputs/cache, output schemas and human review. Provider budgets alone cannot be promised as hard limits.

ATTACK 1 [MAJOR] Workspace invitations lack an acceptance and identity contract
Where: “Membership(tenantId,userId,role,status) grants access”; onboarding is “verify identity → create/join workspace → first project/task → invite teammate”; the delivery phases never specify replacing the existing invitation acceptance semantics.
Problem: The task explicitly requires “authentication versus tenant membership/roles.” That distinction is not carried through invitations, which are a selected launch feature. The retained implementation rejects any already-active global user in server/src/invites/service.ts:46 and rejects an existing account again during acceptance; it creates a global User instead of adding a Membership. Thus a real user in workspace A cannot accept an invitation to workspace B. Also /api/invites/accept is public (server/src/invites/routes.ts:24), and acceptance trusts the bearer token without proving the intended verified identity. “Wrong-account” UI recovery does not define the server rule. Specify tenant-bound, expiring, single-use invitations; intended verified-account matching; atomic membership creation for both new and existing identities; and tests for joining a second workspace, wrong-account acceptance, replay and revocation. Otherwise implementers must invent the security-critical bridge between the proposed identity and membership models.

ATTACK 2 [MAJOR] The proposed CI checks do not close the existing direct-to-production release path
Where: “CI must run frozen-lockfile install, typecheck/build, repaired lint…” and “Reviewer approves diffs, regression evidence and migration risk before any later authorized commit/push.”
Problem: The task requires “meaningful tests and CI/reviewer gates.” The current active .github/workflows/deploy.yml deploys every push to main, with no validation job or dependency on successful checks, and installs an unpinned Railway CLI. Listing CI commands and a review convention leaves that concrete deployment path ungated. For example, a direct main push can still invoke railway up while a separately added isolation-test workflow is failing or pending. Add an explicit work item to require protected-branch review/status checks, prevent unchecked direct pushes, and make deployment depend on the checked commit/artifact; distinguish the present deployment configuration from the intended enforced gate.

ATTACK 3 [MINOR] Retained chat has a verified lost-update defect without a repair task
Where: “Default launch scope is workspaces, invitations, projects and tasks; retain chat”; “Add task versions for conflict detection”; current repairs list “backlog/hierarchy, range constraints, draft loss and output escaping.”
Problem: The backend evidence identifies a separate concurrency defect in server/src/chat/message-service.ts:386–401 and :436–452: reactions are read as a JSON object and rewritten. If A adds one reaction while B adds another from the same starting object, the last write silently removes the other reaction. Task versions do not protect this message write, and socket authorization/durable jobs do not fix it. Because the proposal retains chat and provides an ordered repair plan, include an atomic reaction operation or normalized unique message/user/emoji relation, with a concurrent two-user regression gate. Otherwise this observed data-loss behavior survives the proposed current-repairs phase.

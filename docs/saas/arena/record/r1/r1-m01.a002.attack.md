ATTACK 1 [MAJOR] External customers still hit the existing hard-coded login rejection
Where: “Preserve Google-only, invitation-based beta initially”; phase 2 names “OAuth/CSRF” repairs and phase 5 ships workspace onboarding, but neither identifies or replaces the existing domain restriction.
Problem: The task explicitly states that “Existing login is restricted to @servicebay.ai” and asks for a commercially usable multi-tenant SaaS. server/src/auth/passport-config.ts:63 rejects other domains, independently of Google's hosted-domain hint in server/src/auth/routes.ts:30. An invited customer using owner@customer.example therefore still cannot authenticate even after membership, invitations and workspace onboarding are implemented as described. Google-only identity is compatible with external customers, but retaining this organization-specific admission check is not. The migration needs an explicit change from the hard-coded domain gate to verified identity plus invitation/membership authorization, with a non-servicebay customer regression gate before the beta.

ATTACK 2 [MAJOR] “Repair hierarchy” leaves the known cycle and concurrent-move defects without a usable contract
Where: Phase 2 says “Repair ... hierarchy/backlog”; the architecture specifies “Composite foreign keys enforce matching tenant/project parents,” and phase 4 says “Repair invalid ranges/hierarchies before CHECK/FK/NOT NULL validation.”
Problem: The repository's hierarchy defect is more than invalid stored ranges: server/src/tasks/service.ts:567–595 rejects direct self-parenting but permits moving a task under its own descendant, does not recompute descendant nesting levels, and lacks concurrency protection. With A as parent of B, setting A.parentId=B passes tenant/project composite foreign keys and valid range CHECKs while creating A→B→A; two simultaneous moves can create the same cycle even when each request separately checks ancestry. The proposal acknowledges hierarchy generically but never chooses the transaction/locking or serialization rule, cycle/depth validation, descendant recalculation, or behavioral acceptance cases. That leaves implementers guessing on a source-confirmed backend gap the requested architecture decision is supposed to resolve; migration validation alone does not prevent it recurring.
